# 技術選定書

> 対象プロジェクト：書類・プリント管理アプリ（仮）
> 参照ドキュメント：要件定義書 v7.2
> 作成日：2026年6月22日

---

## 1. 選定方針

本プロジェクトは開発チーム4人・実装期間10日間（前後の準備期間を含め4週間）でMVPを完成させ、成果発表会（デモ本番）で安定稼働させることを目的とする。この制約下で、以下を優先順位の高い順に技術選定の判断基準とする。

1. **開発スピード／学習コストの低さ**：短期間で4人がキャッチアップできること。エコシステムが成熟しドキュメントが豊富な技術を優先する。
2. **実装難易度の低減**：認証・決済・画像配信・非同期処理など枯れた領域は自前実装せず、マネージドサービス（Firebase Auth、Stripe、Cloudinary、SendGrid）に委譲する。
3. **デモ当日の可用性・安定性**：審査期間中にサーバーやOpenAI連携が落ちないこと。インフラはマネージドPaaS（Vercel、Render等）を用い、運用負荷を最小化する。
4. **型安全性・保守性**：4人体制での並行開発において、型不一致による事故を防ぐため、フロント（TypeScript）・バック（Pydantic/SQLAlchemy）双方で型を強制する。
5. **要件定義書で既に確定済みの技術選定との整合性**：要件定義書 v7.2「10. 制約事項・前提条件」にて技術スタックは既に最終確定されているため、本書はその選定理由・比較根拠・リスクを明文化し、チーム内の合意形成と新規参加者のオンボーディング資料として機能させることを目的とする。

## 3. 比較サマリ

### 採用技術

- **Next.js（App Router）**：レスポンシブ対応必須（全画面）、かつチームメンバーの習熟度が比較的高いReact系フレームワークの中で、ルーティング・SSRの実装コストが最も低いため採用。
- **FastAPI**：OpenAI Structured Outputsとの統合がPydanticベースのスキーマ定義で直感的に行えること、非同期処理（async）がCelery・外部API呼び出しの多いこのシステムの構成に合致するため採用。
- **Celery（Worker + Beat）+ Redis**：リマインドメールの「N日前送信」「毎月1日0時の自動リセット」という2種類の定期/予約タスク要件（FR-009, FR-011）を、Beatによるスケジューリングと Worker によるリトライ可能な非同期実行の組み合わせで実現できるため採用。
- **Firebase Auth**：自前のパスワード管理・認証ロジック実装を避け、開発リソースをコア機能（AI解析・カレンダー・通知）に集中させるため、v7.2で自前認証から切り替えて採用。
- **Cloudinary（署名付きURL）**：画像のセキュア配信要件（非認証ユーザーからのアクセス遮断）を、自前の署名ロジック実装なしにSDKレベルで満たせるため採用。

### 不採用技術・判断根拠

- **Django（DRF）**：機能は十分だが、OpenAIのStructured Outputs（JSON Schema）との統合や非同期I/O処理においてFastAPI＋Pydanticの方が実装コストが低く、10日間の実装期間に適さないと判断し不採用。
- **MongoDB等のNoSQL**：書類・グループ・通知スケジュール間のリレーション（外部キー制約、ステータス管理）が要件として明確であり、リレーショナルモデルの方が整合性管理がしやすいため不採用。
- **自前JWT認証**：認証フロー（パスワードリセット、メール確認等）をゼロから実装する工数が、4週間・4人体制のスケジュールに対してリスクが高すぎると判断し、v7.1→v7.2の改訂でFirebase Authへ切り替え。
- **AWS（ECS/EC2による自前インフラ構築）**：本番運用の柔軟性は高いが、IaC・ネットワーク設計・スケーリング設定等の運用工数が、デモ本番までの短期開発フェーズには過大であるため不採用。PaaS（Vercel/Render）を優先。
- **Datadog等の高機能監視SaaS**：必要十分な可観測性はPaaS標準ログ + Sentryで満たせるため、追加コスト・追加学習コストを避けて不採用（将来的な本格運用フェーズでの再検討候補とする）。

## 4. リスクと対応

| 採用技術                       | 懸念点                                                                                                                    | 緩和策                                                                                                                                                                                                                                                                                                           |
| ------------------------------ | ------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| OpenAI API（GPT-4o等）         | レスポンス遅延・解析失敗時に書類登録フローが止まる可能性がある。                                                          | 指数バックオフによる自動リトライ（最大3回）をバックエンド側で実装。解析失敗時は確認画面（UI-004）の各フィールドを空欄表示にし、手入力へスムーズに移行できるUXをフォールバックとして用意（要件定義書 リスク1・リスク2参照）。                                                                                     |
| Firebase Auth                  | サービス側障害時にログイン機能全体が停止するリスクがある。第三者サービスへの認証委譲によりカスタマイズ性が制限される。    | デモ期間中はFirebaseのステータスページを事前確認し、障害発生時の代替手段（テストアカウントでの事前ログイン保持等）を準備する。要件として必要なカスタムフロー（招待機能等）はアプリ側DB（`invitations`テーブル）で別途管理し、Firebase側の責務をID検証のみに限定する。                                            |
| Celery（Worker + Beat）+ Redis | 非同期タスクの設計・デバッグはチームにとって比較的習熟度が低く、スケジュール漏れ・タスク重複実行のリスクがある。          | `notification_schedules`テーブルのステータス（`pending`/`sent`/`failed`/`cancelled`）と`retry_count`で全タスクの状態を可視化し、デバッグを容易にする。BE②担当の負荷集中を避けるため、Week2でLLM連携・Stripeを優先実装し、Celery通知実装はWeek3に着手する週次優先度をチームで合意済み（要件定義書 リスク3参照）。 |
| Vercel / Render（PaaS）        | 無料/低価格プランでのリソース制限（スリープ、コールドスタート等）によりデモ本番中にレスポンス遅延が発生する可能性がある。 | デモ本番前に有料プランへの切り替え、またはウォームアップ用の定期pingを設定し、コールドスタートを回避する。                                                                                                                                                                                                       |
| Stripe                         | Webhook処理の実装不備により、課金状態とアプリ内の`plan_status`に不整合が生じるリスクがある。                              | Webhookイベントの署名検証を必須化し、決済関連の状態変更は冪等性を保った実装にする。MVP範囲では決済導線の表示と基本フローの動作確認を優先し、エッジケースは公開後の改善課題として明示する。                                                                                                                       |
| Cloudinary（署名付きURL）      | 署名付きURLの有効期限切れにより、画像の再取得が必要になるケースでUXが損なわれる可能性がある。                             | フロントエンド側で画像読み込み失敗時に再取得（バックエンド経由でURLを再発行）するリトライロジックを実装する。                                                                                                                                                                                                    |
