# チーム開発 運用ルール

---

## 1. ブランチ運用

### ブランチ構成

```
main          # 本番リリース用（直接pushしない）
develop       # 開発の統合ブランチ
  └── 各自の作業ブランチ
```

### ブランチ命名規則

| 種別         | 形式           | 例                     |
| ------------ | -------------- | ---------------------- |
| 機能追加     | `feature/内容` | `feature/login-screen` |
| バグ修正     | `fix/内容`     | `fix/login-error`      |
| ドキュメント | `docs/内容`    | `docs/meeting-notes`   |

- **言語は英語** を基本とする
- 単語の区切りは `-`（ハイフン）を使う
- 日本語・スペース・大文字は使わない

### 作業の基本フロー

```bash
# 1. developの最新を取得
git checkout develop
git pull origin develop

# 2. 作業ブランチを作成
git checkout -b feature/xxxx

# 3. 作業 → add → commit → push
git add .
git commit -m "feat: ○○機能を追加"
git push origin feature/xxxx

# 4. GitHubでPull Requestを作成
```

## 2. コミットメッセージ

### 形式

```
<prefix>: 変更内容を日本語で簡潔に書く
```

### プレフィックス一覧

| prefix     | 使いどき                                     |
| ---------- | -------------------------------------------- |
| `feat`     | 新機能の追加                                 |
| `fix`      | バグ修正                                     |
| `docs`     | ドキュメントの追加・修正                     |
| `style`    | コードのフォーマット修正（動作に影響しない） |
| `refactor` | リファクタリング                             |
| `chore`    | 設定ファイルなど雑務系                       |

### 例

```
feat: ログイン画面を追加
fix: パスワードバリデーションのエラーを修正
docs: 企画レビュー議事録を追加
```

### NG例

```
# ❌ 何をしたか分からない
git commit -m "修正"
git commit -m "update"
git commit -m "あああ"

# ✅ 何をしたか一目でわかる
git commit -m "fix: ログインボタンが押せないバグを修正"
```

## 3. Pull Request（PR）

### PRを出すタイミング

- 1つの機能・対応が完了したとき
- レビューしてほしいときはWIPでも出してOK（タイトルに `[WIP]` をつける）

### PRの書き方

`.github/pull_request_template.md` にテンプレートを用意しています。
PRを作成すると自動で入力欄に反映されるので、各項目を埋めて提出してください。

| 項目                    | 内容                                 |
| ----------------------- | ------------------------------------ |
| 概要                    | このPRで対応した内容を簡潔に記載する |
| 対応Issue               | `Closes #Issue番号` の形式で紐づける |
| 実装内容                | 具体的に何を実装したか               |
| 実装理由                | なぜその方針にしたか                 |
| 確認内容                | レビュアーに見てほしいポイント       |
| 後続Issueで対応する内容 | 今回スコープ外にしたこと             |
| 補足                    | 共有事項があれば                     |

### マージのルール

- **自分のPRを自分でマージしない**
- 最低1人のレビュー・承認をもらってからマージする
- マージ後は作業ブランチを削除する

## 4. 報連相の粒度

### 基本的な考え方

> 「迷ったら報告する」を徹底する。  
> 小さな共有がチーム全体の手戻りを防ぐ。

### 報告すべきタイミング

| タイミング   | 内容                                                 |
| ------------ | ---------------------------------------------------- |
| 作業開始時   | 何のブランチを切って何をするか                       |
| 詰まったとき | **30分悩んだら相談する**（1人で抱えない）            |
| PR作成時     | Slackなどでチームに声をかける                        |
| マージ完了時 | developが更新されたことをチームに共有                |
| 作業終了時   | 今日やったこと・明日やることをデイリースクラムで共有 |

### 相談するときのポイント

```
❌「エラーが出て動きません」

✅「○○をしたら△△というエラーが出ました。
   □□を試しましたが解決しませんでした。
   ○○のファイルの✕✕行目が怪しいと思っています。」
```

- **何をしたか・何が起きたか・何を試したか** の3点を伝える
- エラーメッセージはコピペで共有する
- スクリーンショットも積極的に活用する

---

## 5. 初心者が特に気をつけること

### ✅ やること

- `main` と `develop` に直接 push しない
- 作業前に必ず `git pull` で最新を取得する
- こまめにコミットする（1コミット1変更を意識）
- 困ったらすぐ相談する

### ❌ やらないこと

- `git push -f`（強制push）は原則禁止
- 大量の変更を1コミットにまとめない
- PRを出さずに直接 develop にマージしない
- エラーを1人で長時間抱え込まない
