## 2. プロジェクト概要

**システム名：** Scanly

**システムの目的：**
家庭や学校で届く書類（プリント）を、スマホで撮影するだけでOpenAIのマルチモーダル能力を活用して自動で「種類・期限」を解釈し、アプリ内カレンダーへ自動登録・通知を行うシステム。

**関係者：**

- 講師：エンジニアスクール講師
- 開発チーム：4人（期間：4週間 / 公開前提）

## 4. 業務フロー（As-Is / To-Be）

### 現在の業務（As-Is）

1. 書類が届くが、後回しにして積み重なる。
2. 処理する際、「いつまでか？」を人間が毎回読み解く（高い解釈コスト）。
3. 各自の手帳やカレンダーアプリに手動で書き写す、または家族に口頭やLINEで連絡する（共有漏れや期限忘れが発生）。

### 新システムでの業務フロー（To-Be）

1. ユーザーはメールアドレスを必須として新規登録（UI-001）を行う。この際、1人利用時にも即座にシステムを利用できるよう「個人グループ」が自動生成される（リマインド日数はデフォルトで「3日前」に設定される）。追加で他メンバーを招待して共同利用することも可能。
2. グループ内は「メンバー全員が同等の権限」を持ち、誰もが書類の登録・編集・削除を行うことができる。ただし、誤操作によるグループ全体の消失を防ぐため、「グループの削除」のみ作成者（`created_by`）に制限される。
3. 書類が届いた瞬間、ユーザーはスマホで「写真を撮るだけ」。
4. バックエンドでOpenAI APIが自動で書類の意味（期限・種類）を解釈。
   > ※AI解析に失敗した場合は、プレースホルダーや空欄の状態で編集画面を表示し、手入力を促すUXとする。
5. 解析確認画面にて、AIの抽出結果をユーザーがその場で必要に応じて修正・編集した上で、登録ボタンを押す。**【v7.5追加】このとき、登録先のグループも選択する。ユーザーが複数グループに所属している場合は、画面上にグループの選択肢が一覧表示され、デフォルトでは最初に取得したグループ（多くの場合は個人グループ）が自動選択された状態になる。ユーザーは必要に応じて登録先グループを変更できる。**
6. 登録完了後、選択されたグループのカレンダーへ即時自動反映される。
7. 同時に、グループ内の他メンバーのアプリ内ヘッダーにある「🔔（ベルマーク）」にお知らせ（「〇〇さんが書類を登録しました」）が即時表示される。
   > ※書類を登録した本人の画面にはこの通知は表示されない。
8. 登録された書類のタスク（提出や支払いなど）が完了したら、ユーザーは詳細画面から「済スタンプ」を付与でき、カレンダー上でも一目で完了状態がわかるようになる。このとき、まだ送信されていない未来のメールリマインドタスクは自動的にキャンセルされる。
9. ユーザーが設定画面で指定した日数（デフォルト3日前）になり、かつタスクが完了（済）になっていない場合、登録されているメールアドレス宛に「リマインドメール」が自動送信される。

## 8. データ要件（スキーマ詳細）

### 主なデータエンティティ（PostgreSQL）

#### 1. `users`（ユーザー情報）【v7.6で変更】

| カラム                 | 型          | 備考                                                                                              |
| ---------------------- | ----------- | ------------------------------------------------------------------------------------------------- |
| `id`                   | UUID        | PK                                                                                                |
| `firebase_uid`         | VARCHAR     | 必須・一意。Firebase Authが発行するUID                                                            |
| `email`                | VARCHAR     | 必須・一意                                                                                        |
| `display_name`         | VARCHAR(50) | 必須。グループメンバー一覧等で表示する名前。                                                      |
| `plan_status`          | VARCHAR     | 初期値: `'free'`                                                                                  |
| `monthly_scan_count`   | INTEGER     | 初期値: 0、毎月1日AM0:00（JST）にCelery Beatでリセット                                            |
| `remind_days_before`   | INTEGER     | 必須、初期値: 3                                                                                   |
| `email_notify_enabled` | BOOLEAN     | 必須、初期値: `true`。【v7.6追加】falseの場合、メールリマインドを送信せずアプリ内通知のみとする。 |

> **注記：** 認証はFirebase Authに委譲するため `password_hash` カラムは不要。バックエンドはFirebaseが発行するIDトークンを検証し、`firebase_uid` でユーザーを特定する。
>
> **注記（v7.4）：** `display_name`の入力経路（新規登録フォームでの直接入力か、Firebase Authの表示名をそのまま流用するか）は実装側で確認が必要。既存ユーザーが存在する状態でNOT NULL列を追加するため、マイグレーション時の既存データ補完方法もBE①と要確認。
>
> **注記（v7.6）：** `email_notify_enabled` はグループではなくユーザー（個人）に紐づく設定のため、同じグループ内のメンバーでも各自異なる設定が可能（設計上正しい挙動）。デフォルト値が `true` のため、`display_name` のときと異なりNOT NULL列追加に伴う複雑なマイグレーション手順（既存データの個別補完）は不要。
>
> **注記（v7.5）：** #27のE2E確認時点で、新規登録フォーム（UI-001）に`display_name`の入力欄が未実装であることが判明している。現状は`POST /v1/auth/signup`に空のリクエストボディが送信され、バックエンドの必須チェックにより422エラーとなる。FE側の対応待ち。

#### 2. `groups`（共有グループ情報）

| カラム       | 型      | 備考                                                |
| ------------ | ------- | --------------------------------------------------- |
| `id`         | UUID    | PK                                                  |
| `name`       | VARCHAR | 必須                                                |
| `created_by` | UUID    | FK → `users.id`。グループ削除はこのユーザーのみ可能 |

#### 3. `group_members`（中間テーブル）

| カラム     | 型   | 備考             |
| ---------- | ---- | ---------------- |
| `id`       | UUID | PK               |
| `group_id` | UUID | FK → `groups.id` |

## 11. リスクと対応方針

| リスク                                               | 対応方針                                                                                                                                                                                                               |
| ---------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| リスク1：OpenAIやメール送信等の外部API通信失敗・遅延 | 指数バックオフによる自動リトライ（最大3回）をCelery Worker側で実行する。リトライのたびに `notification_schedules.retry_count` をインクリメントし、3回失敗した時点で `status='failed'` に確定させエラーログに記録する。 |
| リスク2：AI解析失敗時のUX                            | 確認画面（UI-004）にて「解析ができませんでした。手動での入力をお願いします」等のアナウンスと共に各フィールドを空欄で表示する。ユーザーがストレスなくその場で手動登録へ移行できるUXとする。                             |
| リスク3：BE②担当範囲の過負荷                         | LLM連携・Stripeの基本実装をWeek2で優先し、Celery通知はWeek3に着手する週次優先度をチームで合意する。                                                                                                                    |

## 付録：OpenAI Structured Outputs スキーマ定義

FR-003で使用するLLMレスポンスのJSONスキーマ（BE②とFEのインターフェース合意用）

| フィールド名   | 型               | NULL可 | 説明                                                                        |
| -------------- | ---------------- | ------ | --------------------------------------------------------------------------- |
| `title`        | string           | No     | 書類のタイトル（例：「遠足のお知らせ」）                                    |
| `category`     | string           | Yes    | カテゴリ名（例：「学校」「医療」）。不明な場合はnull。                      |
| `deadline`     | string (ISO8601) | Yes    | 期限日（例：「2026-07-01」）。期限なし・読み取り不能の場合はnull。          |
| `has_deadline` | boolean          | No     | 期限の有無。deadlineがnullでも明示的に「期限なし」と判断できる場合はfalse。 |
