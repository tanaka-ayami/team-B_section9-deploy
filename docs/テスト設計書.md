## 1. テスト方針

### 目的・品質ゴール

本アプリは家族間での書類共有を担う生活密着型アプリであり、以下を品質ゴールとする。

- **機能の正確性**：撮影→AI解析→登録→カレンダー反映→通知の一連のフローが、ユーザーの操作通りに動作すること
- **認証・認可の堅牢性**：他グループのデータに不正アクセスできないこと。招待フローで本人確認が正しく機能すること
- **データ整合性**：書類登録・削除・済スタンプ操作が、関連テーブル（`notification_schedules`・`app_notifications`等）まで正しく波及すること
- **デグレードなし**：新機能追加・バグ修正のたびに既存機能が壊れていないことを確認できること

### カバレッジ目標

| 対象 | 目標 |
|------|------|
| バックエンド（Python/FastAPI）単体テスト | ライン 70% 以上 |
| フロントエンド（Next.js）コンポーネントテスト | 主要コンポーネント（AuthForm・DocumentCard等）のレンダリング確認 |
| E2Eテスト | MVPの6ステップ（ログイン〜通知）が全シナリオグリーン |

### テストピラミッドの考え方

```
        ▲
       / \
      / E2E\        少数・重要シナリオのみ（手動 + 一部自動化）
     /──────\
    /  結合   \      APIエンドポイント単位（pytest + Supertest）
   /────────────\
  /   単体テスト  \   関数・コンポーネント単位（最多）
 /────────────────\
```

- **単体テスト**を最も多く書き、バグを早期に検出する
- **結合テスト**でAPIの入出力・DB操作・認証チェックを確認する
- **E2Eテスト**はユーザーの主要導線（MVPの6ステップ）に絞る。全操作をE2Eにするとメンテコストが高いため、重要シナリオのみ
- Week2時点では時間的制約からE2Eは**手動テスト**を中心とし、#27（フルフローE2E確認）にて実施済み

## 3. テストケース管理

### 管理場所

- **バックエンド単体・結合テスト**：リポジトリの `backend/tests/` 配下にpytestファイルを格納
- **フロントエンド単体テスト**：リポジトリの `frontend/__tests__/` または各コンポーネントの隣に `.test.tsx` として格納
- **E2Eテストシナリオ（手動）**：本設計書（テスト設計書）の「2. 実施済みテスト」テーブルで管理

### ID採番ルール

```
[種別]-[対象機能]-[連番]
例：
  UT-AUTH-001  （単体テスト / 認証 / 001番目）
  IT-NOTIFY-003（結合テスト / 通知 / 003番目）
  E2E-MVP-006  （E2Eテスト / MVPフロー / 006番目）
```

### 不具合のチケット化フロー

```
E2Eテスト中にバグ発見
  → GitHubにissueを作成（#27のチェックリスト「バグは各担当にIssueを作って報告する」）
  → ラベル付与（担当者ラベル・week2等）
  → 修正PRでissueをCloses #XXとリンク
  → PRマージでissue自動クローズ
```

## 4. テスト環境

### 開発/ステージング/本番の差分

| 項目 | 開発環境（local） | ステージング | 本番 |
|------|----------------|------------|------|
| 起動方法 | `docker compose up` | TBD（Render等） | Vercel / Render |
| データベース | ローカルPostgreSQL（Docker） | ステージングDB（独立） | 本番DB |
| Firebase | 開発用プロジェクト | 同左 or 本番と共用 | 本番プロジェクト |
| OpenAI API | 実APIキー（.envで管理） | 実APIキー | 実APIキー |
| SendGrid | 実APIキー（テスト用メール可） | 実APIキー | 実APIキー |
| Cloudinary | 同一アカウント（フォルダで分離推奨） | 同左 | 本番 |
| `FRONTEND_BASE_URL` | `http://localhost:3000` | ステージングURL | 本番VercelURL（#11で要変更） |

### テストデータ作成方針

- **pytestのfixture**（`backend/tests/conftest.py`）でテスト用ユーザー・グループ・書類を生成し、テスト終了後にロールバック
- **手動E2E用テストデータ**：ローカルDockerのDBに対してAdminerで直接作成・削除。本番DBには投入しない
- **テストアカウント**：Firebase AuthのテストプロジェクトまたはDevelopment環境で専用アカウントを用意。実在するメールアドレスを使用する場合はチーム共有のテスト用アドレスを利用
